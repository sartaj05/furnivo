# Furnivo free deployment guide

This guide is designed for a free preview, testing, or early client-demo deployment. Free hosting is not a guarantee of production uptime: Render Free web services sleep after 15 minutes without inbound traffic, and their filesystem is ephemeral.

## Recommended architecture

- Frontend: Render Static Site or Vercel Hobby for a personal/non-commercial project.
- API: Render Free Web Service using the included `render.yaml`.
- Database: Supabase Free PostgreSQL.
- Product images and field proof files: Cloudinary Free plan.
- Notifications: Furnivo in-app notifications first; add an HTTP email provider later.

Do not use SQLite or `backend/uploads` as permanent hosted storage. Use Supabase PostgreSQL and Cloudinary before real deployment.

## One-time provider setup

### Supabase

1. Create a Supabase project.
2. Copy its pooled PostgreSQL connection string.
3. Use it as Render's `DATABASE_URL`.
4. Keep `AUTO_SEED=false` on Render.
5. Run migrations from a trusted local environment before using the live database:

```bash
$env:DATABASE_URL="your-supabase-connection-string"
$env:FLASK_APP="backend.app"
flask db upgrade
```

The current application still supports SQLite locally. Hosted deployments should use PostgreSQL because Render Free local files are lost on restart, redeploy, or sleep.

### Cloudinary

1. Create a Cloudinary account and copy the environment URL.
2. Add it only as a backend secret:

```env
CLOUDINARY_URL=cloudinary://API_KEY:API_SECRET@CLOUD_NAME
CLOUDINARY_FOLDER=furnivo
```

3. Product images use `/api/uploads/product-image`.
4. Field proof images use `/api/uploads/field-proof`.

Never put `CLOUDINARY_URL`, `API_SECRET`, `SECRET_KEY`, or `JWT_SECRET_KEY` in React code, Git, or `VITE_*` variables. Cloudinary signed uploads must be generated by the backend.

## Render deployment

1. Push this repository to GitHub.
2. In Render, choose **New → Blueprint** and select the repository.
3. Review `render.yaml`.
4. Create the API service and static frontend service.
5. Set these Render values:

### API service

```text
DATABASE_URL          = Supabase PostgreSQL URL
FRONTEND_ORIGINS     = https://YOUR-FRONTEND-URL
CLOUDINARY_URL       = Cloudinary secret URL
SECRET_KEY            = generated secret
JWT_SECRET_KEY        = generated secret
AUTO_SEED             = false
ENVIRONMENT          = production
```

Render uses `/api/health` as the health check path. The endpoint performs a database query and reports the configured storage provider.

### Frontend service

```text
VITE_API_URL = https://YOUR-API-NAME.onrender.com/api
```

After the first API deploy, replace the placeholder frontend/API URLs in the Render dashboard and redeploy the frontend.

## CI/CD release gate

`.github/workflows/ci.yml` runs backend tests, migration checks, frontend tests, and the production build on every pull request and push. On a successful push to `main`, it triggers Render only when this GitHub secret exists:

```text
RENDER_DEPLOY_HOOK_URL=https://api.render.com/deploy/srv-...
```

If `FURNIVO_HEALTH_URL` is also configured, the workflow waits for `/api/health` to return successfully after the deploy starts. The Render start command runs `flask db upgrade` before Gunicorn, so schema changes are applied before the API accepts traffic.

## Keeping the free API warm

The repository includes `.github/workflows/health-check.yml`. It calls the deployed health endpoint every five minutes:

1. In GitHub repository settings, open **Secrets and variables → Actions**.
2. Add:

```text
FURNIVO_HEALTH_URL=https://YOUR-API-NAME.onrender.com/api/health
```

3. Run the workflow once from the **Actions** tab to verify it.

GitHub scheduled workflows can run no more frequently than every five minutes, and scheduled jobs can be delayed. The workflow is a best-effort warm-up and health monitor; it cannot guarantee uptime on a free provider. The API must still tolerate cold starts and the first request can be slow.

## Vercel frontend alternative

If you use Vercel instead of the Render Static Site:

1. Import the GitHub repository.
2. Set the project root to `frontend`.
3. Build command: `npm run build`.
4. Output directory: `dist`.
5. Set `VITE_API_URL` to the Render API URL.

Vercel Hobby is intended for personal, non-commercial projects. Use the plan appropriate to your client/business use.

## Deployment checklist

- [ ] Supabase PostgreSQL URL configured.
- [ ] Cloudinary secret configured only on the backend.
- [ ] `AUTO_SEED=false`.
- [ ] Strong generated Flask and JWT secrets.
- [ ] `FRONTEND_ORIGINS` contains only the deployed frontend URL.
- [ ] `VITE_API_URL` points to `/api` on the deployed backend.
- [ ] `/api/health` returns `ok: true`.
- [ ] Admin login works.
- [ ] Product image upload returns a Cloudinary URL.
- [ ] Field proof upload returns a Cloudinary URL.
- [ ] Supabase database tables exist after migration.
- [ ] GitHub `FURNIVO_HEALTH_URL` secret is configured.
- [ ] Demo passwords and demo seed data are removed or changed before real client use.
- [ ] A manual database export is tested before importing real customer data.

## General guide for future projects

For any small full-stack project, keep the same order:

1. Make the app stateless and move database/files to managed services.
2. Add one unauthenticated health endpoint that checks only critical dependencies.
3. Put every secret in the hosting provider's secret manager.
4. Add a reproducible build/start command and a deployment manifest.
5. Add CI checks before enabling automatic deploys.
6. Add an external health monitor, logs, backups, and a rollback path.
7. Test a cold start, a failed database connection, an expired token, and an oversized upload.
